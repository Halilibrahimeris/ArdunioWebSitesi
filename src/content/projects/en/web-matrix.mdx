This project is a special one: the **first to use the board's WiFi**, and it
needs no extra parts. You can build it with nothing but the board and a USB
cable.

What it does sounds simple — type on your phone, see it on the board. But four
layers are working together behind the scenes.

<WiringDiagram file="06-web-matrix.svg" caption="The path text takes from browser to LED matrix" />

## This project is project 5 in reverse

In project 5 the microcontroller did the talking: it read a sensor and pushed
it to Linux with `Bridge.notify()`.

Here **Linux does the talking**: it takes text from the browser and sends it to
the microcontroller with `Bridge.call()`.

| | Caller | Callee |
| --- | --- | --- |
| **Project 5** | MCU: `Bridge.notify("store_reading", …)` | Python: `Bridge.provide("store_reading", …)` |
| **Project 6** | Python: `Bridge.call("show_text", …)` | MCU: `Bridge.provide("show_text", …)` |

The pattern is identical: **one side announces a function, the other calls it
by name.**

<Step n={1} title="Create the app">

In App Lab choose **Create → New App** and name it `write-from-web`.

Open `app.yaml` and add the `web_ui` brick:

```yaml
name: Write From The Web
icon: ✍️
description: Scrolls text typed in a browser across the LED matrix

bricks:
  - arduino:web_ui
```

That single line gives you a working **web server and WebSocket connection**.
You install no Flask, open no ports, and write no WebSocket protocol code.

</Step>

<Step n={2} title="Why can the matrix not render text?">

The board's 8×13 LED matrix is not a text display — it is a grid of 104 pixels.
You cannot tell it to "write HELLO"; you have to light every pixel yourself.

So the sketch defines its own **3×5 font**. Each letter is 3 columns wide and 5
rows tall, and one column is stored as a single byte:

```
  . # .      column0 = rows 1,2,3,4  →  0b11110 = 0x1E
  # . #      column1 = rows 0,2      →  0b00101 = 0x05
  # # #      column2 = rows 1,2,3,4  →  0b11110 = 0x1E
  # . #
  # . #
```

That is the letter **A**. Bit 0 is the top row, bit 4 the bottom.

<Callout lang="en" variant="tip" title="Why three pixels?">
The matrix is 13 columns wide. With 3-pixel letters, three of them fit on
screen at once and the scroll reads smoothly. A 5-pixel font would look nicer
but only two letters would fit.
</Callout>

</Step>

<Step n={3} title="Write the sketch">

Paste the sketch from the **Code** section below into `sketch/sketch.ino`.

Three functions are announced inside `setup()`:

```cpp
Bridge.provide("show_text",      show_text);
Bridge.provide("set_brightness", set_brightness);
Bridge.provide("set_speed",      set_speed);
```

The Linux side can now call any of them by name.

The scrolling happens in `loop()`, again **without any delay**:

```cpp
if (millis() - lastScrollAt < (unsigned long)scrollMs) return;
```

You know this pattern from project 1. It matters especially here, because new
text can arrive over Bridge mid-scroll — a board sitting in a `delay()` would
miss it.

</Step>

<Step n={4} title="Write the Python — and clean the incoming data">

Paste the Python code into `python/main.py`.

The most interesting part is the `sanitise()` function:

```python
def sanitise(raw: str) -> str:
    text = str(raw).translate(ACCENT_MAP).upper()
    text = "".join(ch if ch in ALLOWED else " " for ch in text)
    text = " ".join(text.split())
    return text[:MAX_LENGTH]
```

It does four jobs at once:

1. Folds accented characters to plain ones (Ç → C, Ğ → G)
2. Converts to uppercase — the font has no lowercase
3. Replaces anything it does not recognise with a space
4. Truncates to 60 characters

<Callout lang="en" variant="warning" title="This is a security boundary">
**Never** trust what arrives from a browser as-is. A user can send 10,000
characters, an emoji, or a symbol you never anticipated. Without sanitising,
that would overflow the sketch's 64-character array and hang the board.

The rule applies to every web application, not just Arduino ones.
</Callout>

</Step>

<Step n={5} title="Add the web interface">

Put `index.html` and `app.js` into the `assets/` folder (both are in the Code
section below).

The **order** of the three script tags at the end of the HTML matters:

```html
<script src="libs/socket.io.min.js"></script>
<script src="libs/arduino.js"></script>
<script src="app.js"></script>
```

`arduino.js` needs `socket.io`, and `app.js` needs the `WebUI` class from
`arduino.js`. Reorder them and the browser console reports "WebUI is not
defined".

<Callout lang="en" variant="info" title="Why do the sliders send on a delay?">
There is a small `debounce()` helper in `app.js`. Dragging the brightness
slider makes the browser fire dozens of events a second, and sending every one
of them to the board is pointless traffic. With a 120-millisecond delay only
the final value goes out. The pattern is called *debouncing*.
</Callout>

</Step>

<Step n={6} title="Run it and open it on your phone">

Press **Run**. App Lab shows you the web interface's address — usually the
board's IP address and a port number.

Type that address into your phone's browser.

<Callout lang="en" variant="danger" title="You must be on the same WiFi network">
If your phone and the board are on different networks the page will not load.
If your phone is on mobile data, switch to WiFi. You can check which network
the board joined from the App Lab terminal.
</Callout>

<Step n={7} title="Try it">

1. Type something and press **Send**. The text starts scrolling on the matrix.
2. Drag the **brightness** slider. The matrix responds instantly.
3. Drag the **speed** slider. The scroll slows down or speeds up.
4. Type something accented, like `CAFÉ`. The matrix shows `CAFE`.
5. **Open it on a second device.** Change the text on one and the "Currently on
   the matrix" line updates on the other too.

That fifth point matters: Python broadcasts a `state` message to **every**
connected browser on each change, so two phones never fall out of sync.

</Step>
