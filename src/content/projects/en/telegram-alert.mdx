In the WiFi projects so far you had to be **on the same network** to reach your
board. Here the board goes out to the internet: you can message it on Telegram
from anywhere in the world and ask about your room.

<Callout lang="en" variant="info" title="This bot answers questions">
The bot is built to reply when you ask. It does not message you the instant
motion happens; instead it accumulates events and summarises them when you type
`/status`.

That has an advantage: you are not drowned in dozens of notifications through
the day. You ask when you want to know.
</Callout>

<Step n={1} title="Create a bot on Telegram">

Open Telegram and find **@BotFather** — Telegram's own official bot for making
bots.

1. Type `/newbot`
2. Give your bot a name (for example "Room Watcher")
3. Give it a username, which must end in `bot` (for example `roomwatcher_bot`)

BotFather replies with a long **token**, something like:

```
7123456789:AAExampleTokenDoNotUseThisOne_abcdefg
```

<Callout lang="en" variant="danger" title="That token is a password">
Anyone holding this token has complete control of your bot. Do not screenshot
it, do not send it to anyone, do not put it in your code.

The next step stores it safely.
</Callout>

</Step>

<Step n={2} title="Store the token as an environment variable">

We do **not** write the token into the code. Instead we put it into App Lab's
environment variable settings:

| Variable name | Value |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | The token BotFather gave you |

The `telegram_bot` brick reads the token from there. It appears nowhere in your
code.

<Callout lang="en" variant="warning" title="Why does this matter so much?">
Imagine sending your code to a friend, pushing it to GitHub or pasting it into
a forum. With the token in the code, everyone who sees it owns your bot.

Kept in an environment variable, you can share the code freely — the token
stays behind. The rule applies to every API key: weather services, cloud
providers, payment systems.
</Callout>

</Step>

<Step n={3} title="Find your user ID and add it to the whitelist">

Find **@userinfobot** on Telegram and send it any message. It replies with your
user ID — a long number.

Put that number into the list in `python/main.py`:

```python
ALLOWED_USERS = [
    123456789,   # ← your own ID
]
```

<Callout lang="en" variant="danger" title="Do not leave this list empty">
Your bot's username is guessable. Without a whitelist, **anyone** who finds it
can type `/status` and learn whether there is movement in your room.

You would have built a system that tells strangers whether you are at home.

The line `TelegramBot(whitelist_user_ids=ALLOWED_USERS)` solves this on its own
— everyone not on the list is ignored.
</Callout>

</Step>

<Step n={4} title="Wire the PIR sensor">

The HC-SR501 has three pins:

| Sensor | To the board |
| --- | --- |
| VCC | **5V** |
| OUT | **D2** |
| GND | **GND** |

<Callout lang="en" variant="tip" title="No voltage divider this time">
In project 3 the HC-SR04's ECHO pin drove 5V and a divider was mandatory.

The HC-SR501 is different: it runs on 5V but its **output is 3.3V TTL**. You
can connect it straight to D2.

This is exactly why "it runs on 5V so its output must be 5V" is a bad
assumption. Every module needs its datasheet checked separately.
</Callout>

There are two orange potentiometers on the sensor:

- **Sensitivity** — how far it detects (3-7 metres)
- **Delay** — how long its output stays HIGH after triggering

Start with both in the middle.

<Step n={5} title="The sketch: catch the rising edge">

The sketch's job is simple, but there is a subtlety. A PIR sensor holds its
output HIGH for several seconds after triggering. If we asked "is it HIGH?"
every pass and reported, one movement would produce hundreds of reports.

Instead we catch the **rising edge** — the moment it goes from LOW to HIGH:

```cpp
if (motion && !lastMotion) {
  // Only movement that has just started
}
```

On top of that there is a cooldown:

```cpp
if (millis() - lastReportAt >= COOLDOWN_MS) {
```

Someone walking around a room triggers the sensor continuously. A five-second
cooldown counts that as one "there was movement" event.

</Step>

<Step n={6} title="The Python: define the commands">

`bot.add_command()` binds each command to its own function:

```python
bot.add_command("status", command_status, "Show the motion status")
```

The third parameter is the description Telegram shows in its command menu.

One thing deserves attention in the `/weather` command — it reaches out to the
internet, and the internet does not always work:

```python
try:
    forecast = weather.get_forecast_by_city(city)
    sender.reply(f"{city}: {forecast.category}")
except Exception as error:
    sender.reply("Could not get the forecast...")
```

<Callout lang="en" variant="tip" title="Wrap every network call">
A request to the internet can fail for many reasons: the network drops, the
service goes down, the city is not found. Without `try/except` that failure
crashes the whole app, and your `/status` command stops working too.

Telling the user "that did not work" beats crashing silently.
</Callout>

</Step>

<Step n={7} title="Run it and start talking">

Press **Run**. The App Lab output should show:

```
Telegram bot ready.
Authorised users: 1
```

Now find your bot on Telegram (search for the username BotFather gave you) and:

1. Type **`/start`** — the bot greets you by name
2. Wave your hand in front of the sensor — an exclamation mark blinks on the matrix
3. Type **`/status`** — you get something like "Last motion: 5 seconds ago"
4. Type **`/weather`** — the forecast for your city arrives
5. Type **`/weather Berlin`** — you can ask about any city

<Callout lang="en" variant="info" title="It really does work remotely">
Switching your phone to mobile data changes nothing. The message reaches your
board through Telegram's servers. You can leave the house and ask from the
other side of the city.

That is the fundamental difference from the earlier WiFi projects: those only
worked within the same network.
</Callout>

</Step>
