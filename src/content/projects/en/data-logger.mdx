    a: >-

      It is created inside the app's python folder. Open the terminal in App

The four projects so far could all have been built with a classic Arduino UNO.
This one can **only** be built with a UNO Q.

The reason is simple: reading sensors is the microcontroller's job, but storing
the readings needs a file system and a database. A classic Arduino has neither.
On the UNO Q, both live on the same board.

<WiringDiagram file="05-data-logger.svg" caption="The path a reading takes from sensor to database" />

## Division of labour

The decision this project asks you to make: which job goes on which processor?

| Job | Processor | Why |
| --- | --- | --- |
| Reading the DHT11 | MCU | Its protocol needs precise timing |
| Reading the LDR | MCU | The analog pins belong to the MCU |
| Validating the data | MPU | Logic, with no timing requirement |
| Writing to the database | MPU | The database lives on Linux |
| Keeping a CSV file | MPU | The file system lives on Linux |

<Callout lang="en" variant="tip" title="The general rule">
The microcontroller **measures**; Linux **thinks and stores**. Keep that split
in mind and you will know where everything belongs in every project from here on.
</Callout>

<Step n={1} title="Prepare the circuit">

Good news: you need no new parts. The DHT11 wiring from project 4 and the LDR
wiring from project 2 stay exactly as they were.

If you took them apart, rebuild:

- **DHT11**: VCC → 3V3, DATA → **D7**, GND → GND (+ a 10kΩ between DATA and VCC)
- **Or a 3-pin DHT11 module**: `VCC` / `+` → 3V3, `DATA` / `OUT` / `S` → **D7**,
  `GND` / `-` → GND. The pull-up is already on the module, so no 10kΩ is needed.
  In the wiring diagram, pick **3-pin module** for the DHT11.
- **LDR**: 3V3 → LDR → **A0**, A0 → 10kΩ → GND
- **Or a 3-pin light sensor module**: `VCC` → 3V3, `S` / `AO` → **A0**,
  `GND` → GND. The LDR's 10kΩ resistor is then not needed. In the wiring
  diagram, pick **3-pin module** for the light sensor.

If your module reads backwards (step 5 of project 2), set `LDR_INVERTED` to
`true` in the sketch.

This project does not need the OLED, but you can leave it connected.

</Step>

<Step n={2} title="Create the app and add the brick">

In App Lab choose **Create → New App** and name it `data-logger`.

Now you edit `app.yaml` for the first time. Open it and write:

```yaml
name: Data Logger
icon: 📈
description: Logs DHT11 and LDR readings on the board's Linux side

bricks:
  - arduino:dbstorage_tsstore
```

Those last two lines are the important part. Adding something to the `bricks`
list makes App Lab prepare that capability for you. Here we ask for a
time-series database — we never install PostgreSQL or create a table; the
brick takes care of it.

<Callout lang="en" variant="warning">
Forget to list the brick in `app.yaml` and the Python side raises
`ModuleNotFoundError` when it starts. The library is not there because you did
not ask for it.
</Callout>

</Step>

<Step n={3} title="Write the sketch — the side that measures">

Paste the sketch from the **Code** section below into `sketch/sketch.ino`.

Two lines deserve attention. First, inside `setup()`:

```cpp
Bridge.begin();
```

This opens the bridge. Leave it out and `Bridge.notify` silently does nothing
— no error either, which makes it hard to spot.

Second, inside `loop()`:

```cpp
Bridge.notify("store_reading", temperature, humidity, light);
```

This calls the `store_reading` function on the Linux side and sends it three
values.

<Callout lang="en" variant="info" title="Why does notify not wait for a reply?">
`notify()` sends the data and carries straight on. It waits for nothing.

When streaming sensor readings that is exactly what you want: there is no
reason for the microcontroller to sit idle while the Linux side is busy. It
throws the reading over and gets back to work.
</Callout>

</Step>

<Step n={4} title="Write the Python — the side that stores">

Paste the Python code into `python/main.py`.

The single most important line here:

```python
Bridge.provide("store_reading", store_reading)
```

It tells Python: *"I have a function called `store_reading`, and the
microcontroller may call it."*

<Callout lang="en" variant="danger" title="The most common mistake">
The string in `Bridge.notify("store_reading", ...)` and the one in
`Bridge.provide("store_reading", ...)` must be **exactly identical**.

One character apart and you get no error message. The sketch says it sent
something, Python receives nothing, and you are left guessing. When something
does not work, **this is the first place to look.**
</Callout>

</Step>

<Step n={5} title="Why validate the incoming data?">

The Python code contains this:

```python
if not (-40 <= temperature <= 80):
    print(f"Skipped an invalid temperature: {temperature}")
    return
```

If a sensor wire works loose or the sensor fails, nonsense values arrive.
Storing them is **worse** than storing nothing — because later, looking at a
graph, you cannot tell real data from junk.

<Callout lang="en" variant="tip" title="Validate at the boundary">
This is a general rule in software: validate data from the outside world at
the point it enters your system. Here the "outside world" is the
microcontroller and the "boundary" is the `store_reading` function.
</Callout>

</Step>

<Step n={6} title="Run it and watch the data">

Press **Run**. Both sides are now running together.

Every five seconds the Python output should show something like:

```
Data logger ready. Waiting for readings from the microcontroller...
[   1] 2026-09-07 15:42:10  23.4°C  48%  light=712
[   2] 2026-09-07 15:42:15  23.4°C  48%  light=698
[   3] 2026-09-07 15:42:20  23.5°C  49%  light=203
```

Notice the light value dropping on the last line — that is a hand over the LDR.

</Step>

<Step n={7} title="Find the stored data">

Your readings now live in two places.

The **CSV file** is the easiest to reach. Open the terminal in App Lab and, in
the app folder, run:

```bash
cat python/readings.csv
```

You will see something like:

```
time,temperature_C,humidity_pct,light_raw
2026-09-07 15:42:10,23.4,48,712
2026-09-07 15:42:15,23.4,48,698
```

Copy that file to your computer and you can open it in a spreadsheet and chart it.

The **database** is for programs. It can be queried with `read_last_sample()`
and `read_samples()` — in project 8 we plot exactly this data in a web
interface.

<Callout lang="en" variant="info" title="How long does the database keep data?">
`TimeSeriesStore()` keeps the last **7 days** by default and drops anything
older. For more, construct it as `TimeSeriesStore(retention_days=30)`. The CSV
file has no such limit; it grows until you delete it.
</Callout>

</Step>
